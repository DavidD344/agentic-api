# ADR-004: Use of LLM for Resolving Lattes Match Ambiguities

## Context and Problem Statement

During the Lattes search step, the system frequently encounters multiple candidates for the same person. The most common case is homonyms: two researchers with identical or very similar names working at different institutions. With 480 scholarship holders to process, manually resolving all ambiguous cases would be costly and slow.

It was necessary to decide how to resolve these cases: with pure code (matching rules), with a dedicated LLM agent, with an external identification API, or with some combination of these approaches.

The original project draft planned a dedicated `genderGuesser_agent` to infer gender via an external API (genderize.io). This decision is also addressed here, since the same logic applies: a dedicated agent was considered and discarded in favor of inline LLM.

## Decision Drivers

- The Lattes text search returns candidates by name similarity, not by identity; false positives are frequent
- Homonyms exist even within a specific area (Computer Science)
- Name + institution matching works well for most cases but fails when the institution abbreviation in CNPq does not exactly match how it appears in Lattes
- An external gender API (genderize.io) adds an external dependency, has a cost, and does not use the full profile context
- A dedicated LLM agent for each subtask (match, gender, area) would multiply call costs and orchestration complexity

## Considered Options

- Pure code with matching rules: normalized string comparison between CNPq and Lattes name and institution
- Dedicated LLM agent per subtask: a `matchingAgent` for Lattes, a separate `genderGuesser_agent` for gender
- Specialized external API: genderize.io for gender, no LLM for match
- Inline LLM within the existing scraper: `lattes_scrape.py` calls the LLM only when code rules were insufficient to decide

## Decision Outcome

Chosen option: "Inline LLM within the existing scraper", because it concentrates decision logic where the data is already available, avoids creating additional agents with orchestration overhead, and uses the LLM only when necessary (genuinely ambiguous cases), keeping costs controlled.

For the `sex_inferred` field, the decision was to absorb it into the semantic inference step via LLM instead of using an external API, because the Lattes summary already contains reliable textual markers (professor/professora, researcher/pesquisadora, doutor/doutora) that the LLM knows how to interpret without needing an external service.

### Consequences

- Positive: the LLM is only called for cases that code alone could not resolve, keeping cost proportional to problem difficulty
- Positive: eliminates dependency on external APIs such as genderize.io
- Positive: the `sex_inferred` field uses the full profile context, not just the name, resulting in more contextualized inferences
- Positive: LLM guardrails (confidence ≥ 0.85, lattes_code must be in the candidate list) prevent the LLM from introducing errors with misplaced high confidence
- Negative: the LLM can make mistakes and introduce a false positive that pure code would have left as `ambiguous`; guardrails mitigate this but do not eliminate the risk entirely
- Negative: the LLM call adds latency to the preview step

## Pros and Cons of the Options

### Pure Code with Matching Rules

- Good, because it is deterministic, auditable, and has no API cost
- Good, because it works well for the simplest cases (the majority of the 480 profiles)
- Bad, because it fails on homonyms, different institution abbreviations, and name spelling variations
- Bad, because matching rules grow increasingly complex as more edge cases are found

### Dedicated LLM Agent per Subtask

- Good, because it isolates responsibility for each task in a separate agent
- Bad, because it multiplies the number of LLM calls for cases that could be handled together
- Bad, because it adds orchestration overhead between agents for a task that can be done inline
- Bad, because the matching context is already available in `lattes_scrape.py`; passing it to another agent requires unnecessary serialization and deserialization

### Specialized External API (genderize.io)

- Good, because it is simple to integrate and does not require LLM
- Bad, because it infers gender from the name alone, without considering the profile context
- Bad, because it adds an external dependency that may change pricing, availability, or usage policy
- Bad, because it does not generalize to other ambiguity cases beyond gender

### Inline LLM within the Existing Scraper

- Good, because it uses data already available in the scraper context, without additional serialization
- Good, because it only calls the LLM when necessary, keeping cost proportional to difficulty
- Good, because guardrails ensure the LLM only promotes a match when confidence is high
- Neutral, because it mixes scraping and decision logic in the same file; internal code organization must be maintained carefully

## More Information

The LLM in the preview step receives only the ambiguous case data and the found candidates: name, expected institution, scholarship level as auxiliary context, summary, external links, and the `lattes_code` of each candidate. It does not receive the full curriculum, only the preview available from the text search.

The LLM decision rule is conservative: it may only promote a case to `matched` if it (1) returns valid JSON, (2) chooses a `lattes_code` from the candidate list, and (3) declares confidence ≥ 0.85. Cases that do not meet these criteria remain `ambiguous` and go to the manual review queue.

The full log of LLM decisions is stored in `llm_review.json` for auditing.
