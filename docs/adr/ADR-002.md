# ADR-002: Use of Playwright for Scraping Dynamically Rendered Pages

## Context and Problem Statement

The system needs to collect data from two primary sources: the CNPq scholarship holder table and Lattes curricula. Both pages use technologies that hinder simple HTTP-based collection: CNPq uses JavaScript to render the table, and Lattes requires interaction with search forms and navigation across multiple pages. It was necessary to choose a scraping approach that would work reliably in this context.

## Decision Drivers

- The CNPq page uses JavaScript to render the scholarship table; a plain HTTP request returns HTML without the data
- Lattes requires interaction with search fields and pagination navigation
- The solution must be reliable enough to process 480 people without frequent manual intervention
- The solution must be easy to inspect and debug when a page changes its structure

## Considered Options

- `requests` + BeautifulSoup directly: makes HTTP requests without executing JavaScript
- Playwright + BeautifulSoup: uses a real browser to render pages, then parses the HTML with BeautifulSoup
- Scrapy: full-featured scraping framework with middleware and pipeline support
- Selenium + BeautifulSoup: older browser automation approach, similar in purpose to Playwright

## Decision Outcome

Chosen option: "Playwright + BeautifulSoup", because it is the only option that reliably handles JavaScript rendering while still allowing BeautifulSoup to handle HTML parsing after the page has loaded.

### Consequences

- Positive: works with pages that depend on JavaScript to render content
- Positive: allows interaction with forms, clicks, and pagination just as a real user would
- Positive: BeautifulSoup keeps parsing simple and readable, separated from browser automation
- Negative: requires Chromium to be installed on the operating system
- Negative: slower than a plain HTTP request, which impacts overall pipeline execution time
- Negative: browser environment may behave differently in headless contexts (CI/CD, servers without a display)

## Pros and Cons of the Options

### `requests` + BeautifulSoup

- Good, because it is simple, fast, and has no heavy dependencies
- Bad, because it does not execute JavaScript; pages that depend on JS return incomplete or empty HTML
- Bad, because it cannot interact with search forms that use JavaScript for submission

### Playwright + BeautifulSoup

- Good, because it uses a real browser and executes JavaScript normally
- Good, because it enables full automation: filling forms, navigating pagination, waiting for page load
- Good, because the resulting HTML can be parsed with BeautifulSoup, keeping parsing simple
- Neutral, because it requires Chromium installed on the system

### Scrapy

- Good, because it is a mature framework with native support for queues, pipelines, and retries
- Bad, because it does not natively support JavaScript (would require an additional middleware such as scrapy-playwright)
- Bad, because it adds an abstraction layer that complicates debugging when page structure changes

### Selenium + BeautifulSoup

- Good, because it is a well-established alternative for browser automation
- Bad, because Playwright is more modern, has better headless support, and a more ergonomic API
- Neutral, because behavior would be equivalent to Playwright for this use case

## More Information

Playwright is initialized in headless mode (no graphical interface) during pipeline execution. To visually inspect what is being collected during development, headless mode can be disabled by passing `headless=False` in the browser configuration.

The separation between automation (Playwright) and parsing (BeautifulSoup) is intentional: when the HTML structure of a page changes, only the parsing logic needs to be updated, without altering how the browser navigates.
