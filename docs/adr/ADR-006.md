# ADR-006: Prefer Reviewable False Negatives Over Silent False Positives

## Context and Problem Statement

During Lattes scraping, the system frequently encounters cases where it cannot confidently identify which curriculum belongs to the person being searched. This occurs due to homonyms, names spelled differently between CNPq and Lattes, or situations where the text search returns many candidates with similar scores.

It was necessary to decide which policy to adopt for these cases: accept the highest-scoring candidate (even with doubt), require resolution before proceeding, or mark as reviewable and continue without blocking the pipeline.

The same dilemma applies to semantic inferences: when the LLM has low confidence about a field (e.g., `sex_inferred = unknown`), should the system force a value, block execution, or mark it as reviewable?

## Decision Drivers

- Associating the wrong curriculum with a person introduces incorrect data that can silently propagate through the entire pipeline
- Forcing the resolution of all ambiguous cases before proceeding blocks the pipeline until a human intervenes
- The project has a deadline and it is not feasible to block everything because of a few ambiguous cases
- A silent false positive is more dangerous than a documented false negative: the former appears correct but is not; the latter is visible and traceable

## Considered Options

- Accept the highest-scoring candidate: when in doubt, the system automatically chooses the most probable candidate
- Block the pipeline until resolved: ambiguous cases prevent advancement to the next step
- Mark as reviewable and continue: ambiguous cases go to `review_queue.csv` and the pipeline advances without them; they are excluded from subsequent steps

## Decision Outcome

Chosen option: "Mark as reviewable and continue", because it allows the pipeline to process the 479 safe cases while the few ambiguous cases are documented and awaiting resolution, without introducing incorrect data into the dataset.

### Consequences

- Positive: the pipeline is not blocked by ambiguous cases; the 479 safe cases are processed normally
- Positive: ambiguous cases are documented with a reason in `review_queue.csv`, making later review straightforward
- Positive: a run is not promoted to active if it still has a non-empty review queue, preventing incomplete data from reaching the dashboard
- Negative: cases in the review queue do not appear in the final dataset until resolved; this may leave the dataset with fewer entries than expected
- Negative: someone must periodically inspect the review queue

## Pros and Cons of the Options

### Accept the Highest-Scoring Candidate

- Good, because it simplifies the pipeline and guarantees a curriculum for each person
- Bad, because it silently introduces incorrect data when the highest-scoring candidate is wrong
- Bad, because errors introduced here propagate to all subsequent steps (full, inferences, dashboard, chat)
- Bad, because there is no way to know afterward which profiles were accepted with doubt

### Block the Pipeline Until Resolved

- Good, because it guarantees that no ambiguous data advances
- Bad, because it makes the pipeline fragile: any ambiguous case blocks processing of all others
- Bad, because it is impractical in real scraping where ambiguous cases will always exist

### Mark as Reviewable and Continue

- Good, because the pipeline is not blocked by minority cases
- Good, because cases are documented with a reason, enabling human or LLM review afterward
- Good, because the LLM automatically attempts to resolve ambiguous cases before they reach the manual queue
- Good, because active run promotion checks whether the queue is empty, preventing partial runs from going to production
- Neutral, because it requires periodic queue inspection; acceptable since the system goal is reliable data

## More Information

The review queue operates at two levels:

**Level 1 — Automatic LLM review:** at the end of the preview step, `ambiguous` cases are sent to the LLM, which attempts to choose the correct curriculum with confidence ≥ 0.85. In the most recent full run, 3 out of 4 ambiguous cases were resolved this way.

**Level 2 — Manual review:** cases the LLM could not resolve remain in `review_queue.csv` with a documented reason. A human can create a `review_resolved.csv` with their choices, and the system merges it via the `resolve-review` command.

This same principle applies to inferences: fields with `needs_review=true` appear in `inference_review_queue.csv`. The system operates normally with those fields marked; review is a subsequent process, not a blocker.
