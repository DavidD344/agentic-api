# ADR-003: Separation of Scraping from the API Layer (router→service→scraper)

## Context and Problem Statement

The system has two distinct responsibilities: collecting and enriching data (scraping) and exposing that data over HTTP (API). It was necessary to decide how to organize the code: place scraping logic directly inside API routes, or clearly separate these two responsibilities into distinct layers.

This question is especially relevant because scraping involves browser automation, HTML parsing, retries, timeouts, and matching decisions. Mixing this with the HTTP layer would make it difficult to test, debug, and evolve either part independently.

## Decision Drivers

- Scraping is inherently unstable and needs to be tested and run independently of the API
- The API must have a predictable response time; scraping can take minutes and must not block HTTP requests
- Collection steps need to be run via CLI before becoming endpoints, in order to validate data quality
- Mixing browser automation with HTTP routing makes the code hard to maintain and debug

## Considered Options

- Scraping logic directly in routes: API routes directly call Playwright, parse the HTML, and return the data
- Three-layer separation (router→service→scraper): scrapers are independent modules; services coordinate business rules; routers only expose HTTP
- Scrapers as asynchronous workers: scrapers run in background workers (Celery, RQ) decoupled from the API

## Decision Outcome

Chosen option: "Three-layer separation (router→service→scraper)", because it is the only option that allows scrapers to be run via CLI independently, and keeps the HTTP layer focused solely on exposing data, with no knowledge of browser behavior, HTML, or matching decisions.

### Consequences

- Positive: scrapers can be run, tested, and debugged via CLI without starting the API
- Positive: routes have no knowledge of browser, HTML, or matching; they simply call a service
- Positive: when the API exposes the pipeline as an endpoint, the route will call a service that calls the same already-existing scraper, with no code duplication
- Positive: collection logic can evolve without changing the HTTP interface
- Negative: creates more files and more indirection, increasing the initial learning curve

## Pros and Cons of the Options

### Scraping Logic Directly in Routes

- Good, because it is simple and has no indirection for small projects
- Bad, because it mixes responsibilities: the route must know how to open a browser, parse HTML, and make matching decisions
- Bad, because it makes it impossible to run scraping via CLI for validation before exposing it through the API
- Bad, because slow scraping directly blocks the HTTP server

### Three-Layer Separation (router→service→scraper)

- Good, because each layer has a single, well-defined responsibility
- Good, because scrapers can be run via CLI during development and validation
- Good, because adding new scrapers (Google Scholar, for example) does not require changing upper layers
- Neutral, because it requires discipline to prevent business logic from leaking into routes or scrapers

### Scrapers as Asynchronous Workers

- Good, because it fully decouples scraping execution time from API response time
- Good, because scraping can be scaled independently of the API
- Bad, because it adds additional infrastructure (a message broker, workers) that increases complexity
- Bad, because it is harder to debug and to verify that data was correctly processed after async handling

## More Information

The current code direction is:

```
router → service → scraper
```

Scrapers are still CLI-executable today because we are validating data quality first. When the API exposes the pipeline, the route must call a service; it must not know how to click on pages, parse HTML, or decide Lattes matches.

Scrapers live in `app/scrapers/` and are independent Python modules that can be imported by both the CLI orchestrator and the API's future services.
