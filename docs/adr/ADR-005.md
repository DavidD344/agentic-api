# ADR-005: Precomputed Semantic Inferences Before Chat and Dashboard

## Context and Problem Statement

The system needs to respond to natural language queries about researcher profiles (FR04) and provide metrics to a dashboard (FR02). The raw full curriculum of each person can have hundreds of thousands of characters (median 179k, maximum 827k in the current run). It was necessary to decide how to process this data so that queries are fast and cost-efficient.

The core question is: do we send each person's full curriculum to the LLM for every query (real-time RAG approach), or do we generate a structured semantic profile per person before the chat begins?

## Decision Drivers

- Sending 480 full curricula for every query would be prohibitively expensive and slow
- The dashboard needs aggregated metrics that cannot be generated in real time from raw text
- The fields needed for the dashboard (area, region, career, tags) are the same for all queries
- The LLM answering the professor's queries must not need to re-read all curricula for every question
- Inferences need to be auditable: it must be possible to know where each field came from and with what confidence

## Considered Options

- Real-time RAG: for each query, retrieve relevant snippets from raw text via embeddings and send them to the LLM
- On-demand real-time inference: when the user asks about a person, the LLM reads the full curriculum at that moment
- Precomputed inferences: a separate step (`inference_scrape.py`) generates a structured `semantic_profile` per person before chat and dashboard are used

## Decision Outcome

Chosen option: "Precomputed inferences", because it transforms the raw curriculum into a small, structured profile that can be searched locally and sent as context to the LLM, drastically reducing the cost and latency of each query.

### Consequences

- Positive: each person becomes a compact semantic profile that can be loaded into memory and searched by any field
- Positive: the dashboard can aggregate structured fields without requiring an LLM call per request
- Positive: chat receives only the profiles relevant to the question (top N), not all 480
- Positive: fields have `confidence`, `source`, and `needs_review`, making inferences auditable
- Negative: there is an upfront LLM cost to generate inferences for all profiles before the system can be used
- Negative: if a person's curriculum is updated on Lattes, inferences need to be regenerated

## Pros and Cons of the Options

### Real-time RAG

- Good, because it always uses the most current curriculum data
- Good, because it does not require a separate preprocessing step
- Bad, because it requires generating and maintaining an embeddings index
- Bad, because the cost per query is unpredictable depending on how many relevant snippets are found
- Bad, because structured fields for the dashboard (UF, area, career) do not naturally emerge from similarity searches

### On-demand Real-time Inference

- Good, because it avoids the upfront cost of processing all people
- Good, because it always uses the most current data
- Bad, because sending the full curriculum (up to 827k chars) for every query is expensive and slow
- Bad, because the first query about a person would be much slower than subsequent ones
- Bad, because the dashboard would need to trigger inferences for each person when rendering

### Precomputed Inferences

- Good, because the LLM cost is paid once, not on every query
- Good, because it generates structured fields that the dashboard can use directly without LLM
- Good, because chat can search for the most relevant profiles locally before calling the LLM
- Good, because each field has audit metadata (`source`, `confidence`, `needs_review`)
- Neutral, because reprocessing is required when data changes; acceptable since the pipeline is already periodic

## More Information

The flow of a natural language query with precomputed inferences works as follows:

```
1. API loads profiles_with_inferences.json (once, into memory)
2. Receives the user's question
3. Performs a local search by relevant terms across fields: search_keywords,
   research_topics, methods_and_techniques, qa_context, dashboard_tags
4. Selects the top N most relevant profiles (e.g., top 5)
5. Builds a compact context with those profiles
6. Sends question + context to the LLM
7. Returns the answer
```

This is significantly cheaper and faster than sending all 480 full curricula for every question.

Inferences are generated in 5 calls per person (default `split` mode), covering rule validation, research area, career, experience flags, and dashboard/chat fields. The `single` mode (one call per person) exists as an experimental alternative for cases where speed is the priority.
