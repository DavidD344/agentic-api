# ADR 0004: Chat flow with two LLM agents

Status: accepted

## Motivating Requirement

RF04 requires natural language queries. The initial document planned a `query_agent`, but real questions showed two different needs:

- planning how to query the base;
- writing a useful and validated answer.

## Architectural Problem

A single direct prompt tends to:

- get counts wrong;
- mix examples with totals;
- fail to explain criteria;
- retrieve information without validating context;
- become expensive when given large context.

## Decision

We will split chat into two agents:

```txt
query_planner_agent
  receives the question
  understands intent
  selects the tool
  returns a JSON plan

query_answer_agent
  receives the plan
  receives tool results
  validates when needed
  writes the final answer
```

Default configuration:

```txt
CHAT_PLANNER_MODEL=gpt-5.4-mini
CHAT_MODEL=gpt-5.4-mini
CHAT_TITLE_MODEL=gpt-5.4-nano
CHAT_DISABLE_STRUCTURED_QUERY=0
```

## Rationale

This flow separates reasoning/planning from answer writing. The first agent decides what to do; the backend executes controlled tools; the second agent answers.

This directly fits the requirement to document:

- flow;
- orchestrator;
- handoffs;
- tools;
- guardrails;
- reasoning and planning.

## Resulting Behavior

Base context sent to agents:

```txt
dashboard_metrics_context
minimal_profiles_context_text
recent conversation history
```

The backend may execute:

```txt
structured_query
file_search
local profile/topic search
explanatory fallback
```

The chat title is generated by a third lightweight agent:

```txt
chat_title_agent -> CHAT_TITLE_MODEL=gpt-5.4-nano
```

## Guardrails

- The planner returns JSON, not code.
- The backend does not execute Python generated by the LLM.
- Operators and fields are allowed by code.
- The history sent to the model is limited.
- The final agent must differentiate calculated data, semantic candidates and inferences.

## Consequences

Advantages:

- more reliable answers;
- clear multi-agent architecture;
- better explanation of tools;
- automatic session title;
- ability to validate ambiguous topics.

Limitations:

- two calls increase cost and latency;
- the planner may choose the wrong tool;
- prompts must be maintained well;
- minimal context in every call consumes tokens.
