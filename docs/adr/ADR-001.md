# ADR-001: Pipeline Structured as Isolated Steps with Timestamped Snapshots

## Context and Problem Statement

The system needs to collect data from CNPq, enrich it with information from Lattes, and then generate semantic inferences via LLM. Scraping is inherently unstable: pages change, servers fail, there are homonyms, timeouts, and blocks. It was necessary to decide how to structure the collection process: as a single sequential script that does everything at once, or as separate steps with intermediate checkpoints.

## Decision Drivers

- Scraping fails partially with some frequency; re-running everything from scratch on each failure is costly
- It is necessary to compare different runs to identify regressions or improvements
- Failed runs must not overwrite good data
- Different steps have different failure modes (network, parsing, LLM, homonyms) and need to be debugged independently
- The LLM cost in the inference step is significant; re-running everything because of a scraping error would be wasteful

## Considered Options

- Monolithic pipeline: a single script that executes CNPq → Lattes → Inferences with no checkpoints
- Pipeline with isolated steps and timestamped snapshots: each step saves its results in a timestamped folder and can be re-executed independently
- Pipeline with a database as intermediate state: results are stored in a database instead of files

## Decision Outcome

Chosen option: "Pipeline with isolated steps and timestamped snapshots", because it is the only option that simultaneously satisfies the auditability requirement, the need to re-execute isolated steps, and low setup cost (CSV and JSON files require no additional infrastructure).

### Consequences

- Positive: any step can be re-executed independently without losing the work from previous steps
- Positive: different runs can be compared by inspecting timestamped folders
- Positive: limited-person runs are treated as test samples and do not overwrite production data
- Positive: `current.json` decouples the API from the details of which run is currently active
- Negative: disk usage grows with each run; old runs must be removed manually
- Negative: file paths are passed from one step to the next, creating coupling through file naming conventions

## Pros and Cons of the Options

### Monolithic Pipeline

- Good, because it is simple to understand and run
- Bad, because any failure in any step forces re-running everything from the start
- Bad, because it is not possible to audit the intermediate state of the data
- Bad, because the LLM cost in the inference step would be wasted every time scraping fails before reaching it

### Pipeline with Isolated Steps and Timestamped Snapshots

- Good, because each step can be re-executed independently
- Good, because data from each execution is preserved and comparable
- Good, because it requires no additional infrastructure (only the filesystem)
- Good, because it facilitates human auditing and debugging of problems specific to one step
- Neutral, because it requires a naming convention for folders and files

### Pipeline with a Database as Intermediate State

- Good, because it facilitates querying and filtering of intermediate data
- Good, because it avoids proliferation of files on the filesystem
- Bad, because it requires additional infrastructure (a database) that increases setup complexity
- Bad, because it makes manual data inspection by a developer more difficult

## More Information

The active manifest `scrape_results/current.json` is the central reference the API uses to discover which run is in production. This fully decouples the API logic from the details of which execution was the most recent.

A run is only promoted to active when the full pipeline completes without errors, without skipped entries, and with an empty review queue. Limited runs are never promoted.
